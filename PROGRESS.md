## Decisions
- D-001 Storefront = Next.js (SSR for SEO); Admin = Vite SPA; API = Express + Mongoose; monorepo npm workspaces.
- D-002 No TypeScript; JSDoc for key contracts; zod for runtime validation shared across API/UI.
- D-003 Money in integer halalas (SAR). Stock via append-only ledger.
- D-004 Content fields use `LocalizedString` (`en` source + auto `ar`) from day one; English is the only authored language.
- D-005 First payment gateway adapter: TBD (pick a KSA gateway before P4.1).
- D-006 Translation: eager auto-translate on save/build + cache; on-demand only as fallback; provider via adapter (google|azure|deepl|llm) — first provider = **LibreTranslate, self-hosted** (free, open source, no API key, no per-character cost, text never leaves our servers; added as a docker-compose service in P0.10). Also ship a `noop` provider (translation disabled → storefront falls back to English) selectable in settings. Paid providers stay possible via the adapter, no code change elsewhere. Budget guard still built but defaults to unlimited for self-hosted. Known trade-off: Arabic quality is lower than paid APIs; glossary + optional manual override cover key terms. (User decision 2026-10-08: "use any free translation service or don't do it"). Admin override optional, never required.
- D-007 Language switcher is storefront-only; URL scheme `/ar/...` (default `en` unprefixed). Admin panel UI stays English in v1.

- D-008 ESM (`"type":"module"`) everywhere; Node >=22.12 (`.nvmrc`). API dev uses `node --watch --env-file-if-exists=../../.env` (no nodemon/dotenv). Root `.env` serves API + compose; frontends get their own env in P0.7/P0.8.
- D-009 Mongo dev URI uses `directConnection=true` to the single-node replset (member host `localhost:27017`); transactions verified from host.
- D-010 Architecture boundaries enforced in `eslint.config.js` via `no-restricted-imports` (controller/routes ↛ repo/model, service ↛ model, cross-module only via `index.js`, vendor SDKs only in `adapters/`, packages ↛ apps, client ↛ server libs). Flat config replaces rule options per block, so use the `restrict()` helper when adding blocks.
- D-011 `overrides.shell-quote ^1.12.0` (patched transitive of concurrently, dev only); remove once concurrently ships it.
- D-012 Error body adds `requestId` (additive to `{ error: { code, message, details? } }`) for support/log correlation.
- D-013 Events are in-process and emitted AFTER commit; durable side effects must be enqueued to BullMQ by the subscriber. A transactional outbox can be added later if lost-on-crash events become a problem.
- D-014 Tests: `mongodb-memory-server` replset (real transactions) via `apps/api/test/mongo.js`; Redis integration tests gated by `TEST_REDIS_URL` (CI runs a Redis service). Dev Mongo bumped to `mongo:8.0` to match test binary family.
- D-015 `.env.example` ships working DEV-ONLY secrets so local setup is copy-and-run; `config.js` refuses them when `NODE_ENV=production`.
- D-016 Validator messages are i18n KEYS (`validation.*`, see `validators/messages.js` `V`), never English; API returns them in `error.details[].message`, UI renders `t(key)`. P0.11 must add these keys to `en.json`.
- D-017 Rates (VAT, discounts) are integer basis points (1500 = 15%); rounding = half away from zero, once per computed amount. Line-level vs invoice-level VAT rounding policy is decided in P3.2/P6.1 (ZATCA check).
- D-018 Phone default = KSA mobiles only (`+9665XXXXXXXX`); `phone({ allowInternational: true })` driven by a setting. Business limits (max qty, password policy) are factory params fed from settings; `DEFAULTS` in shared are seed values only.
- D-019 Auth state (password hash, lockout, sessions, one-time tokens) lives ONLY in the auth module's collections (`auth_credentials`, `auth_sessions`, `auth_tokens`). Staff/customers modules register a `PrincipalAdapter` (lookup/profile) in `modules/index.js`; auth never imports them (no cycles).
- D-020 Access token in memory (Bearer) + refresh cookie. CSRF applies only to cookie routes (refresh/logout): `X-CSRF-Protection: 1` header + Origin/Referer allowlist + SameSite=Strict. Requires API and apps on the same SITE (e.g. api.example.com + example.com); set `COOKIE_DOMAIN` accordingly.
- D-021 Every authenticated request checks session liveness in Mongo (indexed `_id` lookup) so revocation is immediate; cache in Redis in P10.3 if needed.
- D-022 Enumeration: login/forgot are generic; ACCOUNT_LOCKED (423) / ACCOUNT_DISABLED (403) only shown after a correct password. Registration returns 409 with conflicting field names (accepted risk, rate-limited); claiming a passwordless guest record must go through email proof (reset flow) — revisit in P3.5.
- D-023 Auth policy (TTLs, lockout, session cap) in `modules/auth/auth.policy.js`; moves to settings `security.*` in P0.6. Password policy default = shared `password()` defaults until P0.6.
- D-024 One-time tokens travel to the email subscriber in the event payload (`auth.passwordResetRequested`, `auth.emailVerificationRequested`); in development only, links are logged (P4.5 adds real email).
- D-025 Branch reach = role `allBranches` flag (HQ/accounting/content) OR the staff member's assigned `branchIds`; super-admin = all. (Chosen over per-role branch lists: simpler, covers the cases; revisit if needed.)
- D-026 Privilege-escalation rules: non-super-admins can only grant/assign permissions and branches they hold, cannot edit roles holding more than they do, cannot edit their own role/status/branches/super-admin flag; super-admin flag only set/changed by super-admins. Seeded roles are templates: inserted once, never overwritten, editable, not deletable.
- D-027 Access is resolved per request from Mongo (staff + role), so role/permission changes apply on the next request. Cache in Redis in P10.3 with explicit invalidation on `role.updated`/`staff.updated`.
- D-028 Settings values are read synchronously from a per-process cache; writers broadcast on Redis channel `supershop:settings:changed`, peers reload; a 60 s periodic reload covers missed messages. A setting key missing from the DB = registry default (only overrides are stored).
- D-029 `PATCH /settings` body is `{ changes: [{ key, value }] }` (not an object keyed by setting key) because setting keys contain dots and the unsafe-key guard rejects dotted object keys.
- D-030 Audit entries are written in-process by event subscribers (best-effort if the process dies between commit and write; failures logged at error). Request IP is recorded for auth events; other entries correlate to HTTP logs via `requestId`. Outbox if stronger guarantees are needed.
- D-031 Auth/staff/customer validation schemas are provided per request via `getSchemas()` (memoized on the relevant settings) so policy changes need no restart.
- D-032 Admin dev uses Vite proxy `/api` → API (same origin, like prod behind Nginx) so cookie/CSRF behave identically; `VITE_API_URL` empty by default.
- D-033 react-router pinned to v7 (v8 available but its API unverified here); shadcn components are hand-written (CLI is interactive) following shadcn source, on the unified `radix-ui` package.
- D-034 Admin bundle ~220 kB gz (React/router/zod/forms); route-level `lazy()` splitting added as feature pages land. Storefront (SEO-critical) is separate.
- D-035 Next.js 16: middleware is now `src/proxy.js` (`export function proxy`); read `node_modules/next/dist/docs` before using Next APIs (bundled docs warn APIs differ from training data).
- D-036 Storefront pages must not read request headers/cookies in shared segments (forces dynamic rendering, losing SSG/ISR) — not-found is a client component for that reason. Personalized bits go in client components or separate dynamic routes.
- D-037 `@next/eslint-plugin-next` not used: it pulls `braces` with an unfixable high advisory; our React rules cover the storefront. Revisit when fixed.
- D-038 Compiler bug workaround: never write `/\u2028/` regex literals in frontend code (Turbopack inlines a raw line separator → broken bundle); build such characters with `String.fromCharCode`.
- D-039 Field components never block a partly-valid insertion: beforeinput cancels only insertions with no valid character; everything else is cleaned on change (mobile keyboards insert whole words).
- D-040 `@supershop/ui` is i18n-agnostic: components take already-translated strings (labels, errors, aria-labels); apps translate validation keys (`fieldMessage` in admin). Apps' CSS must `@source` the package so Tailwind compiles its classes.
- D-041 LibreTranslate batching (q as array) is undocumented → adapter sends one request per text (concurrency 4). Real LibreTranslate container NOT run in-session (Docker Hub rate limit): verify locally with `docker compose --profile translation up -d` + provider setting; pin the image tag then (P10.4).
- D-042 Default provider = `noop` (translation off) so local setups work without the 1–2 GB model download; enabling = start the profile + set `i18n.provider`. Pending items stay `pending` while off; "Retranslate all" (P0.13) recovers them.
- D-043 No `TranslationJob` collection: per-field status lives in `<field>.meta.<lang>` (`pending|done|failed|stale`, provider, at) — queryable for the P0.13 failed-jobs view; BullMQ holds the queue itself.
- D-044 Glossary seed contains only do-not-translate terms (English); preferred EN→AR pairs are admin data (P0.13) — seeding them would mean hand-writing Arabic.
- D-045 Localized models must be saved with `doc.save()` (hooks); after bulk `updateOne`/`updateMany` on localized fields call `scheduleEntityTranslation` explicitly.
- D-046 Mask token format is `[n]` — measured on real LibreTranslate: `⟦n⟧`/`XQnQX` destroyed, `{n}` 3/6 intact, `[n]` 6/6. Provider output is validated: token parity, bracket count, markup injection, length ratio, and "still mostly Latin" for non-Latin targets (`untranslated`).
- D-047 UI strings the engine can't translate are recorded `status: failed` in the lock → English served + CI ⚠ warning (not failure); retried every translate run. Missing/stale/hand-edited/placeholder problems stay hard CI failures.
- D-048 ⚠ QUALITY: Argos (LibreTranslate) en→ar is weak on short UI labels (e.g. "Gadgets"→"gloves", "Home"→"house", "Footer"→"foot"). The pipeline is sound; wording must be fixed by an Arabic speaker via manual overrides / glossary pairs (P0.13) or by switching provider (adapter-ready). Must be reviewed before go-live.
- D-049 LibreTranslate verified as pip package v1.9.6; docker image tag still `latest` (Docker Hub rate-limited here) — pin `v1.9.6` after a local pull (P10.4).
- D-050 Language redirects: an explicit `lang` cookie applies to English (unprefixed) document navigations; auto-detect only with `i18n.autoDetect` (default off); bots (incl. HeadlessChrome) never redirected. Proxy caches public settings 60 s → setting changes reach the proxy within a minute. If a CDN is put in front, it must not cache unprefixed HTML across cookies (or redirects move to the edge) — revisit in P10.4.
- D-051 Fonts self-hosted (Fontsource 5.3.0, OFL): Inter (Latin, 48 KB, preloaded), Noto Sans Arabic (Arabic subset, 166 KB, not preloaded, `unicode-range`). Text in a language the page isn't in (switcher label) uses the system font so it never pulls the other web font.
- D-052 Dates always pass an explicit calendar (ar-SA defaults differ across browsers/ICU); digits: Latin UIs always Western, Arabic UI per `i18n.digitStyle` (default Western).
- D-053 UI string corrections are runtime DB overlays (`ui_string_overrides`), not edits of generated files: CI lock stays meaningful, Arabic speakers fix text without a deploy. Storefront order: en ← generated <lang>.json ← overrides (60 s cache, tag `ui-overrides`). Admin bundles the storefront catalogs read-only via alias `@storefront-i18n`.
- D-054 Per-field "Edit Arabic" for CONTENT (products, pages…) uses `setManualTranslation`/`revertToAuto` from the i18n module inside each entity's own editor (P1.5, P5.x) with that entity's permission — no generic cross-model edit endpoint.
- D-055 All stored images are re-encoded to WebP only (no AVIF output: slow to encode; Next.js `<Image>` can still serve AVIF from these). Originals are NOT kept (smaller attack surface/storage); max stored side = `media.maxDimension` (2560).
- D-056 Media stores storage KEYS, never URLs; URLs are built by the storage adapter at read time (`MEDIA_PUBLIC_URL`), so moving to S3/CDN = new driver + env change, no data migration. In production let Nginx serve `MEDIA_LOCAL_DIR` at `/media` with the same headers (P10.4).
- D-057 Deleting media is a soft delete; files stay so pages/products/orders referencing them keep rendering. A purge job for unreferenced, deleted files comes later (needs usage tracking from P1.4/P5.x).
- D-058 Product/page editors (product.create|product.update|page.manage) may list and upload media (they need it in their editors); renaming/alt edits/deletes in the library need `media.manage`.
- D-059 Identical uploads (same SHA-256 of the uploaded bytes) return the existing item (200 + `meta.duplicate: true`) instead of storing a copy. Concurrent identical uploads may still create two items (harmless; no unique index because of soft delete).
- D-060 Category tree = parentId + materialized `ancestors` (root→parent) + `depth` + `position`. Structural edits (create/move/delete) run in a transaction that bumps counter `guard:category-tree` first → serialized; content edits don't. "Unlimited depth" is capped at 20 levels as a safety ceiling.
- D-061 Admin drag & drop reorders within the same parent only; re-parenting is an explicit "Parent category" choice in the form (moves to the end of the new parent). Avoids accidental drops into the wrong branch; nested-tree drag can be added later without API changes (`/move` already takes any parent + index).
- D-062 Category slugs are English-only `[a-z0-9-]`, auto-generated from the name when omitted (suffix `-2`, `-3`…); explicit duplicates → 409 `SLUG_TAKEN`. Changing a slug does not create a redirect yet (redirects manager P5.5).
- D-063 Public API language: `?lang` → `lang` cookie → `Accept-Language` → English (`requestLanguage` in the i18n module); public responses send `Vary: Accept-Language, Cookie` + `Content-Language`.
- D-064 Brand names are proper nouns: stored as plain strings, never translated. `protectName` (default on) adds the name to the glossary as never-translate; staff turn it off for brands that are common words (glossary matching is case-insensitive, so "Apple" would also freeze "apple juice"). Removing protection later = delete the term in Settings → Languages (never removed automatically).
- D-065 Suppliers accept international phone numbers always (foreign suppliers); KSA mobiles still normalize to +966. KSA landlines must be typed in +966 format. VAT/CR numbers are format-checked only (5–20 letters/digits); ZATCA VAT checksum rules can be added when purchase invoices need them (P2.3/P6.4).
- D-066 Plural UI strings (`t(key, { count })` → `key_one/key_other`) are fine in the English-only admin; avoid them in storefront strings until Arabic plural forms (zero/two/few/many) are supported by the translate pipeline.
- D-067 Product = aggregate root; variants live in their own collection (stock/orders reference variant ids) but are only written through the product (one transaction). PATCH `variants` = the complete set; removed variants are soft-deleted (their SKU/barcode become reusable). Concurrent edits: last writer wins (no form-level version check yet — add `expectedUpdatedAt` if editors collide in practice).
- D-068 Every product has ≥ 1 variant; no options ⇒ exactly one default variant (`optionValues {}`). Max 3 options × 50 values, 250 variants. Option/value keys come from the English text on first save and stay stable (renaming a label keeps the key and the variants).
- D-069 Prices are stored exactly as entered, in the store's price mode (`tax.pricesIncludeVat`, default VAT-inclusive); orders will snapshot price + tax. `taxCategory` (standard|zero|exempt) is per product for ZATCA.
- D-070 Cost is field-level protected: hidden from responses and rejected (403) in writes without `product.viewCost`; omitted cost on update keeps the stored value.
- D-071 Custom field VALUES are never translated (data). To show translatable values on the storefront use `select`/`multiselect` (option labels are auto-translated). `customField.manage` is not in any seeded role (structural setting) — super-admin or a custom role.
- D-072 Product custom field definitions are edited via API now; their admin screen ships with the product UI (P1.5).
- D-073 Variant matrix rebuilds only on structural option changes (value added/removed, option removed, leaving a field) — not per keystroke — so keys come from finished text. Combinations aren't deleted from the table (would come back on the next rebuild); staff switch them off with "Active". Removing a whole option recreates the variants (new SKUs) — a structural change by design.
- D-074 Brand/supplier pickers load the first 100 (A–Z); switch to a searchable combobox when a store passes that.
- D-075 In-store barcodes use GS1 restricted-circulation prefixes 20–29 (setting `barcode.internalPrefix`, default 20; until the General settings tab exists change it via `PATCH /settings`). Sequence = counter `barcode:internal`, never reused. If the store uses price-embedded scale labels (often 20–29 too), pick a different prefix for item codes — scale-label parsing is a POS concern (P6.1).
- D-076 Symbology is derived from the code, not stored: a valid EAN-13/EAN-8/UPC-A prints as such, anything else (SKU-like codes, GTIN-14) as Code 128. Digit-only codes of GTIN length must have a valid check digit; other lengths are accepted as Code 128 content.
- D-077 Scanner detection: ≥ 4 characters, ≤ 50 ms between keystrokes, ending in Enter. Physical key codes are used (Arabic layout safe). Slow Bluetooth scanners may need a larger gap — make it a POS setting in P6.2 if needed.
- D-078 Import file layout = one row per variant keyed by `product_key` (slug), Shopify-like; images are NOT imported in v1 (edit in the product UI). Upsert semantics: a missing column keeps stored values, an empty cell clears; stored variants not in the file are kept (to remove a variant use the editor).
- D-079 Import errors are per product (one bad row fails only its product; others are written). No automatic retries (a job is claimed once; re-running is safe: upsert). Max 10 MB / 10,000 rows / 100 columns; XLSX decompression limits rely on the 10 MB cap (revisit in P10.1).
- D-080 Import/export files live in private storage (`PRIVATE_FILES_DIR`, default `var/private`) — must be outside any web-served path in production. Export downloads are restricted to the job creator (exports may contain cost prices) and expire after 24 h (cleaned up when new jobs start).
- D-081 CSV is handled by our own RFC 4180 code (csv-parse < 7.0.2 has a prototype-pollution advisory and 7.0.3 was days old). XLSX via exceljs 4.4.0 with `overrides.uuid ^11.1.1`. XLSX cells are written as text so prices keep their exact 2 decimals.
- D-082 Built-in search = MongoDB (no extra infrastructure): normalized tokens + anchored-prefix regex on a multikey index, app-side scoring of ≤ 1000 candidates. Fine up to tens of thousands of products (measured 20k: ≤ 0.3 s); beyond that or for typo tolerance/synonyms, add a Meilisearch/Atlas adapter (`adapters/search`, `SEARCH_DRIVER`). No typo tolerance or synonyms in v1; `popularity` is reserved for best-seller ranking (P8).
- D-083 Search index is derived data: rebuilt from products at any time (`POST /search/rebuild`, auto on first start). Sync is in-process via domain events — with several API instances, the instance that handled the write re-indexes. Draft/archived products are indexed but only `active` ones are returned publicly.
- D-084 Arabic search normalization is ours (Mongo text search has no Arabic analyzer): letter-form folding + article stripping, applied identically at index and query time. Arabic characters in source are always written as `\u` escapes / code points (tooling note: the agent shell decodes `\u` escapes in commands, so files were written programmatically).
- D-085 Branch create/delete is reserved for staff whose role covers all branches (HQ); branch-scoped managers may edit and staff only their own branches. Out-of-scope branches answer 404 (existence not revealed). Branches are soft-deleted and only when unused; otherwise deactivate (`isActive: false`).
- D-086 Staff↔branch assignment stays on the staff record (`branchIds`); the branch endpoints are a convenience over `updateStaff` so there is one set of guards. A branch-scoped manager can only change staff whose resulting branches are all inside their scope (multi-branch staff are managed by HQ). Max 500 branches (list is unpaginated).
- D-087 Stock never goes below zero through adjustments, transfers or receipts-reversals: a decrease that exceeds on-hand is refused (409). To correct a wrong number, use a stock count (`counted`), which sets the quantity. Sales can opt into overselling per call (`allowNegative`) once POS policy exists (P6.1).
- D-088 Transfers are immediate (out of the source and into the destination in one transaction); no in-transit state in v1. Both branches must be in the actor's scope (HQ moves stock between other teams' branches). An in-transit/approval flow can be added as new operation types without changing the ledger.
- D-089 Stock documents get gapless numbers per type (`GRN-`, `ADJ-`, `TRF-`); sales and returns don't (their order/receipt number identifies them) to avoid a hot counter on every sale. Received unit cost is stored on the ledger row only; updating variant cost (e.g. weighted average) is left to purchase orders (P2.3).
- D-090 Idempotency for stock writes is built into the operation header (unique `<staffId>:<Idempotency-Key>`), so the replay check is part of the same transaction — no separate idempotency store needed for these endpoints.
- D-091 PO unit costs are excluding VAT and visible to anyone with purchase.view (that is the purpose of the screen); the product's own cost stays behind product.viewCost. Variant cost after a receipt follows `purchase.costMethod` (default `average`: weighted over on-hand in all branches; negative/zero on-hand or no prior cost → received cost).
- D-092 Receiving is limited to what is still outstanding on the PO (no over-receipt); extra goods = edit the PO first or use a plain stock receipt. Partially received POs are closed, not cancelled; POs are never deleted.
- D-093 Stock history shows the staff member's name to anyone who can view inventory (accountability on shared stock); no other staff details are exposed. Stock screens list branches through `GET /inventory/branches` (scope only), so stock roles don't need branch.view.
- D-094 Storefront images use the media pipeline's stored WebP sizes (thumb 320 / md 800 / lg 1600 / full) via `srcset` + `sizes` on a plain `<img>` with width/height, lazy loading and `fetchpriority` for the LCP image — not `next/image` optimization (would re-encode already-optimized files and Next 16 refuses to optimize images from local/private IPs, i.e. our API host). Switching to a CDN later = change `MEDIA_PUBLIC_URL`.
- D-095 Public stock is in/out only (no quantities), computed from branches flagged "fulfils online orders"; with no such branch everything shows out of stock. Search listings have no "in stock only" filter yet (the search index has no stock data) — revisit with the cart (P3.2/P3.3).
- D-096 Listing URLs: `/category/<slug>` (slugs are globally unique, so subcategories need no parent path), `/product/<slug>`, `/search`. Filtered/sorted listings are `noindex,follow` with canonical to the plain category; search results are always noindex. Prices in listing URLs are whole SAR.
- D-097 Carts store quantities only; price, VAT and stock are recomputed on every read (the catalog is the source of truth). Corrections (quantity capped, price changed) are applied and reported once via `notices`. Out-of-stock / unavailable lines stay visible (excluded from totals) so the shopper sees what happened instead of items silently disappearing.
- D-098 The cart reveals the sellable maximum per line (`maxQty` = min(setting, online stock)) so the stepper can stop at it; public product pages still show only in/out of stock (D-095). Guest → customer merge happens lazily on the first cart request carrying both the guest cookie and a customer token (no coupling to the login endpoint); quantities are summed.
- D-099 VAT is computed per line and summed (as on ZATCA invoices); tax categories `standard` (setting rate), `zero`, `exempt` (0%).
- D-100 Product cards are client components (swatches, quick add, quick view) rendered inside server pages; their HTML is still server-rendered (SEO unaffected). Swatches use the first option whose values have colours; up to 8 per card.
- D-101 "Buy now" = add to cart (without opening the mini-cart) and continue to `CHECKOUT_PATH`; the cart is kept, so the item is not bought in isolation. P3.4 points `CHECKOUT_PATH` at the checkout.
- D-102 Animations use `motion` with `LazyMotion(domAnimation)` and always honour "reduce motion". Layout animations (which need the larger feature set) are avoided.
- D-103 Local dev infrastructure on macOS runs through Homebrew, not Docker: one `mongod` (`/opt/homebrew/etc/mongod.conf`, `replSetName: rs0`, loaded as the keg's own launch agent because `brew services start mongodb-community` breaks when the tap's formula version moves past the installed keg) plus `brew services start redis`. A standalone `mongod` has no transactions, so `npm run seed` and every money/stock write fail against it — `npm run infra:local` starts the services, initiates `rs0` and checks `maxmemory-policy=noeviction`. The docker-compose stack stays supported (same ports, so run one or the other).
- D-104 The storefront's `<html>`/`<body>` carry `suppressHydrationWarning`: browser extensions (launchers, password managers, Grammarly…) add attributes to them before React hydrates, which React reports as a hydration mismatch on every page. It silences attribute diffs on those two elements only — mismatches the app itself produces are still reported.
- D-105 Customer self-service lives under `/api/v1/account` (profile + addresses from the customers module, `/account/orders` from the orders module). The id always comes from the session — no endpoint takes a customer id — and every route is Bearer-only with `Cache-Control: private, no-store`.
- D-106 Saved addresses are subdocuments on the customer (max 10), not their own collection: they are only ever read with their owner. The whole array is rewritten on each change (guarded by `updatedAt`) so "exactly one default" is decided in one place; deleting the default promotes another.
- D-107 An account is linked to past GUEST orders only when the email is PROVEN — the verification link or an identity provider that vouched for it — never by matching an address at sign-up. The orders module subscribes to `auth.emailVerified`; OAuth sign-in emits the same event, so there is one path.
- D-108 Google sign-in is a server-side redirect flow (`/start` → Google → `/callback`): the code is exchanged server-to-server and the profile read from `userinfo`, so no ID-token verification and no token in any URL; the session arrives as the normal refresh cookie. The state cookie is SameSite=Lax (Strict is not sent on the return navigation), `returnTo` must be a path on our own site. Credentials are settings, not env, so a shop can turn it on without a deploy; unconfigured = 404.
- D-109 The storefront keeps the access token in memory only and restores sessions with ONE refresh call on mount; concurrent refreshes share a single in-flight promise because refresh tokens rotate and reuse is treated as theft (React's double-mount in dev would otherwise burn a session). Account pages render nothing personal on the server, so they stay cacheable and are `noindex`.
- D-110 Public tracking answers with its own DTO (`toTrackingDto`), not the order: number, status, placed/updated dates, name, city, lines, total and payment state. Knowing an order number and a phone should show where the parcel is — not the street address, email or custom-field answers that the order also holds (§5.1 PII minimization).
- D-111 The customer-facing timeline is four steps (placed → processing → shipped → delivered) with a status→step map in `packages/shared`, so storefront and (later) admin draw the same thing; statuses that end an order replace the steps with one sentence. When P4.3 makes the lifecycle configuration, this map moves with it and no UI changes.
- D-112 `/track` is indexable (people search for it) but only the FORM is server-rendered; the order is fetched client-side, so nothing personal is cached or indexed. A confirmation page link carries `?order=<number>` only — never the phone, which the visitor types (no personal data in URLs).
- D-113 First gateway = **Moyasar** (user's choice, replaces the TBD in D-005), hosted invoice flow: the customer pays on Moyasar's page (Mada, cards, Apple Pay, STC Pay), so no card data touches this server and PCI scope stays out of the project. Amounts are halalas on both sides. Written from the published API shape — verify against a sandbox account with real keys before go-live.
- D-114 A gateway result is applied in ONE place (`applyResult`), reached by the webhook AND by the customer returning (the confirmation page syncs a pending payment). Whichever arrives first wins, the second changes nothing (`processedEvents`), so neither a lost webhook nor an impatient customer leaves an order wrong. A paid amount that differs from the order's total is refused and logged — never silently accepted.
- D-115 A failed or abandoned payment leaves the order `pending` with its stock still held, and the confirmation page offers a fresh payment page. Cancelling and restocking is the state machine's job (P4.3); doing it here would race the gateway's own retries.
- D-116 Payment records live in their own `payments` collection (one per attempt, financial record, never deleted); the order keeps a summary (`payment.method/status/gatewayRef/refundedAmount`) so order screens and receipts need no join. Refunds are made against the captured charge (`chargeRef`), not the invoice.
- D-117 Webhooks are verified by the gateway's own secret (constant-time compare) and nothing else: no session, no CSRF (a browser never sends one), raw bytes kept for gateways that sign them. An event for an unknown reference answers 200 so the gateway stops retrying something that was never ours; an unverifiable one is 401.
- D-118 What a shop accepts is DATA (the `payment_methods` collection), not settings or code: enable, rename, reorder, price and extend without a deploy. Only `type` carries behaviour — `gateway` (hosted page), `cod`, `offline` (the shop collects it) — so a shop inventing "pay at the branch" needs no new code. The two built-in keys are seeded and cannot be deleted: checkout knows how to finish them and old orders name them.
- D-119 A method's fee is `fixed + percentage of (goods + delivery)`, computed by the pure `paymentFee()` the storefront and API share, and carries VAT exactly like delivery (`paymentCharge`). The order stores it as `totals.paymentFee` plus a snapshot of the method (key, type, label as the customer saw it, fee) — a renamed or deleted method never changes an old order or receipt.
- D-120 Checkout takes the method KEY as a slug and checks it against the shop's own list server-side (enabled, in range, gateway configured). An unknown or unavailable method is refused BEFORE the order is created, so no stock is taken for an order nobody can pay for.
- D-121 The order lifecycle is CONFIG, not code: one shared file lists states, transitions, the actor allowed (`staff` | `system`), guard NAMES and the event each move emits. Services never compare statuses by hand, and the admin builds its buttons from `allowedTransitions()` — changing the flow is an edit in one file. Guards are named in the config and implemented in the API, because they need payments, shipments and stock.
- D-122 A cancellation restocks from the LEDGER, not from the order: `reversalLinesFor()` reads what the sale operations actually moved, so the goods return to the branches they left even when an order was filled from several. Status change, history entry and the stock return are one transaction, and the move is applied only `from` the status it was read in, so two staff cancelling at once cannot restock twice.
- D-123 Money before cancellation: a PAID order cannot be cancelled until its payment is refunded (`moneyReturned` guard) — cash on delivery cancels freely. A refund itself never restocks; goods coming back are a return (P6.6). Adding a shipment IS shipping the order: the tracking number is what the shop and the customer both act on.
- D-124 Staff order endpoints (`/api/v1/orders`) ship with the state machine rather than with the screens (P4.4), so the lifecycle is usable and tested on its own. Cancelling is its own permission (`order.cancel`) because it moves both money and stock.
- D-125 The admin never lists what an order "can do": the buttons come from the order's `nextActions` (the lifecycle config + its guards, P4.3), each carrying the reason it is blocked. A flow change is a config edit, and staff always see WHY something is unavailable instead of a missing button.
- D-126 The invoice is part of the order page, hidden on screen and shown only when printing (`print:` utilities), so the browser's own print dialog produces it: no PDF service, no second fetch, and what staff read is what prints. The ZATCA tax-invoice QR, VAT number and shop address join it in P6.4.
- D-127 Internal notes (`order.notes[]`, who/when/text) are separate from the customer's checkout note and never leave the admin — the tracking and account views assert they don't. The staff NAME is stored with the note, like the stock history (D-093), so the record still reads correctly after someone is renamed or leaves.
- D-128 Both notification channels default to the `log` provider: a shop that has not configured mail or SMS sees the exact message in the application log rather than losing it quietly, and local development needs no mail server. Switching to SMTP or a KSA provider is a settings change (adapter + registry), never a deploy.
- D-129 Every message is sent in the CUSTOMER's language (`order.lang`, or the customer's own for account mail), never the staff member's. Templates are `LocalizedString`, so staff write English once and Arabic is generated like any other content; `{{variables}}` are already protected by the translation pipeline's placeholder parity check.
- D-130 Nothing is ever sent without BOTH an enabled channel and an enabled template, and every attempt — sent, failed or skipped — is written to `notification_logs` with the provider's own words. The order never waits for a mail server: subscribers enqueue, the worker sends, failures retry. A failure cannot break the thing that happened.
- D-131 SMS has two KSA providers (Unifonic, Taqnyat) rather than one, because the choice was still open and each is one small REST file — a shop picks in settings. Both are written from published API shapes and need a real account to verify before go-live, like the payment gateway (D-113).
- D-132 BullMQ reserves ':' in job ids (it builds Redis keys from them) and rejects the enqueue outright — found by running the real flow, not by the tests, which call the sender directly. `enqueue()` now sanitizes ids centrally so no caller has to remember.
- D-133 A block type is declared once in the shared registry (props, which are translatable, defaults, version); the storefront renderer, the admin props panel and the translation pipeline all read that declaration. Adding a section type is a definition plus a renderer — no schema, router or migration work. Unknown block types RENDER AS NOTHING rather than throwing, so a page saved by a newer deploy never breaks an older one.
- D-134 A page's customer-facing text is mirrored out of the blocks into a flat `texts` array keyed `<blockId>.<prop>`, because the translation engine works on array paths (`texts.*.value`): pages then get staleness, manual overrides, retranslate-all and the failed-jobs view with no special cases. `props` always keeps the English source, so a page renders before any translation exists.
- D-135 A translation is shown only when it was made from the English the rendered blocks carry (`value.en === props[prop]`). The text list follows the DRAFT, so a published page whose draft has moved on shows its own English instead of a translation of something else — a visitor never reads a sentence the shop did not publish.
- D-136 Builder HTML is sanitized ONCE, server-side on save (DOMPurify + jsdom, allow-list of tags/attributes/URL schemes); the renderers then print it without thinking. Publishing deep-copies the draft, since block props are `Mixed` and a shallow copy would leave the live page pointing at objects the builder keeps editing.
- D-137 `@supershop/ui` components that hold React state now carry `'use client'`: the storefront renders pages on the server for SEO, and importing the package's barrel into a server component otherwise fails. `BlockRenderer` and the block components deliberately stay server-renderable.
- D-138 The builder's props panel is GENERATED: each block declares the control it wants per prop (`editors: { level: { control: 'select', options: [...] } }`), so a new block type is editable the moment it is defined — there is no per-block form to write, and the panel cannot drift from the schema.
- D-139 Undo/redo keeps its history in state (not refs): the toolbar renders from it, every change goes through one `commit`, and redo is dropped on a new edit. The builder is keyed by page id, so opening another page starts its own history rather than inheriting the last page's.
- D-140 Autosave saves ~1.2 s after the editor STOPS changing things, never while they type; leaving with unsaved work asks for confirmation, and Publish saves first, so nobody publishes something they cannot see saved. A failed save keeps the work on screen and retries on the next change.
- D-141 Publishing keeps what WAS live as a version (20 kept), and restoring one puts it back into the DRAFT rather than straight onto the site — an editor looks at it and publishes it again.
- D-103 "Stock reserved" at checkout = real ledger `sale` movements at order placement (no reservation state): the conditional `$inc` makes overselling impossible and the ledger stays the single source of truth. Cancellations restock via the order state machine (P4.3). Online orders are fulfilled from branches flagged "fulfils online orders", split across them when one cannot cover a line; `branchId` on the order is the branch that supplied the most lines.
- D-104 Orders start `pending` with `payment.status: 'pending'` and `cod` as the only method until the payment adapters land (P4.1); methods come from `ORDER.PAYMENT_METHODS` so adding one is not a checkout change.
- D-105 The cart must be unchanged while the order is written: emptying it is guarded by the `rev` read at the start of checkout, and a mismatch rolls the whole transaction back (409 `CONFLICT`). `Idempotency-Key` is scoped to the cart (or the customer) so a retry of the same submit returns the first order (`Idempotent-Replayed: true`).
- D-106 The thank-you page is reached with an unguessable one-off token (hash stored on the order), not the order id, so a reload or a bookmark works without exposing other orders. Later lookups use order number + phone (`/checkout/track`, P3.6).
- D-107 Delivery is a flat admin-set fee with an optional free-over threshold and a taxable flag (not a shipping-rate engine); `deliveryMethod` is `delivery` only until pickup/branch collection is requested.

- D-142 Text inside repeated block items is translated by PATH: a block declares `items.*.question` and the page expands it against the real props, producing keys like `blk-faq.items.0.question`. One mechanism covers flat props and lists, so a slide or a question is translated with no per-block code — and reordering items reorders their keys, which is why an auto translation is only used when it was made from the English now in that slot (D-135).
- D-143 A block never fetches: it declares what it wants ("best selling", this category, these brands) and the page resolves everything in one parallel pass, handing it over as `context.data[blockId]`. The storefront renders in a single server pass (no waterfall, no client fetch) and the renderers stay the same dumb components the admin preview uses.
- D-144 The lookups behind that are INJECTED at the composition root, so the pages module still imports no other module. A missing provider yields an empty section rather than an error — a page renders even if a part of the shop is switched off.
- D-145 "Best selling" is counted from orders (units sold in the last 30 days), not from a popularity field nothing writes yet, and which states count as a sale lives in the order flow config (`ORDER_FLOW.sold`) instead of a status list buried in a query.
- D-146 Catalogue pickers keep ids only; what the admin arranged is the order, so the resolver re-sorts whatever the lookups return. Hand-picked products are looked up by id when the panel opens, so the list still reads properly after a reload.

- D-147 A menu item stores WHAT it points at (page/category/brand id, the listing, or an address), not a URL someone copied. The public endpoint resolves the address when it renders, through the same injected lookups the page blocks use (D-144), so renaming a slug or unpublishing a page can never leave a dead link in the navigation — the item simply stops appearing.
- D-148 Menus and the layout are ONE request for the storefront (`/site/public`), because every page needs the header, footer, announcement bar and theme together. It is ISR-cached for 60 s and tagged `site`, so an admin change appears within a minute; on-demand revalidation comes with the rest of the cache work.
- D-149 Theme tokens are the few things that cannot break the design: two colours, a corner radius, and which BUNDLED font is used — never a font URL, since the app self-hosts its fonts on purpose (D-078). Colours are hex-only and anything malformed falls back to the default, because these values are printed straight into CSS.
- D-150 Announcement-bar and footer text are content (LocalizedString, auto-translated), while the theme lives beside them as plain values in the same singleton document — one read for the storefront, and the announcement bar is never half-translated on a cold cache since the English is served until Arabic arrives.
- D-151 The header dropdown is CSS-only (`group-hover` + `group-focus-within`): the header stays a server component, which matters because it is on every page and part of what crawlers read first.

- D-152 Redirects are stored for the language-neutral path and applied in the proxy, before routing: one rule covers `/old` and `/ar/old`, the visitor is answered once (no render, then redirect), and a 410 is a real 410 rather than a rendered 404. The rules are read with a 500 ms timeout and a one-minute cache, and an unreachable API means no redirects rather than a stalled site.
- D-153 robots.txt moved from Next's metadata object to a route, because a shop may add its own lines and those must come out verbatim. Switching indexing off is one decision with two consequences — a blanket disallow AND an empty sitemap — so the two files can never contradict each other.
- D-154 The shop's contact details are split by nature, not by form: the address is content (localized, auto-translated), while phone numbers, emails and profile links are plain strings — they read the same in every language and must never reach a translation provider (§5.7).
- D-155 Social profiles are a fixed list of platforms with full https addresses, so the footer can label them without a shop pasting arbitrary markup, and the logo/favicon/sharing picture are media ids — the same library, the same re-encoding and size variants as any other upload.
- D-156 Any API error carrying field `details` is shown beside the field in these forms, not only a 422: a clashing redirect (409) is a field problem to the person typing it, and a toast would hide which field it was about.

- D-157 The starting home page is DATA, seeded like roles and payment methods: ordinary blocks, published, with nothing the builder cannot reach. There is no "default template" code path in the storefront to drift from what a shop sees — the only built-in layout left is the fallback for a shop with no home page at all.
- D-158 The seed never rewrites an existing home page, so running it on every deploy is safe: a shop that reworded its hero or deleted the page keeps that decision.

- D-159 A counter sale is an ORDER, in the same collection with the same lifecycle and the same stock ledger — `channel: 'pos'`, numbered `POS-…`, created `paid` then `completed` in one transaction. Reports, returns (P6.6) and the admin screens therefore work on POS sales without a second code path.
- D-160 The till never sends money. It sends what the cashier did; prices, VAT, discounts and totals are computed server-side by the one shared `priceSale`, so a tampered or stale screen cannot change what is charged, and the quote endpoint shows the cashier exactly what the sale will cost.
- D-161 A basket discount is spread across the lines (largest-remainder) rather than kept as one lump: each line's VAT stays correct and a partial return reverses exactly what that line was charged.
- D-162 A discount larger than the shop's cap, or larger than what it is taken off, is REFUSED with the field named — never silently clamped. Giving a discount and changing a price are separate permissions, and the refusal is a 403, because it is about who the cashier is, not about what they typed.
- D-163 Payment-method `type` now also decides where a method may be used: `cash` is for the counter (and is the only kind that may be overpaid, with change from the drawer), `gateway` is for the website. `seedPaymentMethods` ensures missing built-ins rather than only seeding an empty list, so this reaches shops that are already running without touching their own edits.
- D-164 The till looks a customer up by phone or email and attaches them when they already have an account; it never creates one. An unknown name and number are snapshotted on the sale instead — a receipt should not quietly open an account for someone.

- D-165 The block renderer's context is DATA only — a language prefix and formatting options, never functions. Two blocks (hero carousel, countdown) run in the browser, and React refuses a function handed to a client component; `@supershop/ui` turns the prefix and options back into links and formatted money on both sides. (Found by opening the seeded home page, not by a test: jsdom does not enforce that boundary.)

- D-166 The till keeps the basket in the browser but never the money: each change asks the server what it comes to (debounced), and the screen shows that answer. While a quote is in flight the last confirmed figures stay up; if it fails the till says the totals are not confirmed and will not ring the sale up.
- D-167 Offline, the till holds its ground instead of guessing: the basket stays and can be put aside, and payment is blocked. There is no offline sale queue in v1 — a sale that nobody priced is not a sale, and stock that moved without the server knowing is worse than a short wait.
- D-168 One `Idempotency-Key` per basket, made when the basket starts and replaced after it is sold: a cashier who taps Complete twice, or whose connection drops mid-request, gets the same sale back (P6.1 handles the replay).
- D-169 The till has its own search endpoint rather than borrowing the catalogue's: one request gives name, SKU, price and branch stock, and a cashier role stripped to `pos.sell` can still sell.

- D-170 The private key that QZ Tray's calls are signed with never reaches the browser: the admin sends the message QZ wants signed and gets a signature back, so a page without a session (or without `pos.sell`/`settings.printing`) cannot drive the shop's printers. The certificate is public by design; the key is an encrypted secret setting, read fresh per call so rotating it takes effect at once.
- D-171 The API decides what a receipt says and which printer it goes to; the browser only carries the bytes. One implementation, testable without paper (`previewLines`), and the same endpoint will serve the editor's preview (P6.4) and any other client.
- D-172 Receipts are built from instructions, not strings: a template is a list of blocks with placeholders, `showIf` and repeating `items`/`payments` — which is what makes P6.4's editor a form over data rather than a code change. Unknown instructions are skipped rather than guessed at, so an older printer layer never garbles a newer template.
- D-173 Width is the printer's, not the template's: every line is wrapped or cut to the paper's character count, including an over-long value in a two-column row — a line wider than the paper prints as rubbish, which is worse than a truncated date.
- D-174 Non-breaking spaces inside formatted money are turned into ordinary ones before the bytes are written (a thermal printer would print '?'), and the same substitution is applied when measuring a line, so what is measured is what is printed.
- D-175 ZATCA Phase-1 Simplified Tax Invoice QR is encoded in `@supershop/shared` (`zatcaQr`: TLV tags 1..5 in UTF-8 → Base64) and rendered to SVG by our own zero-dependency QR encoder (`qrMatrix`/`qrSvg`, ISO/IEC 18004 Model 2, Byte mode, ECC L, versions 1–10) and `<QrCode>` in `@supershop/ui` — used identically on thermal receipt previews, ESC/POS QR blocks, and the printable A4 `OrderInvoice`. When `tax.vatNumber` is empty, `zatcaQr` returns `''` and the QR block is omitted.
- D-176 Receipt and label templates are singletons (`receipt_templates` / `label_templates`, `key: 'default'`) holding structured config (language `en|ar|bilingual`, dimensions in mm, field toggles, logo media id, and `LocalizedString` header/footer/labels) that `buildReceiptTemplate` and `buildLabelTemplate` compile into the ESC/POS instruction list — both API print jobs and the admin's instant live preview run the exact same compiler.
- D-177 `encodeText` in `escpos.js` preserves UTF-8 bytes for Arabic Unicode (`0x0600..0x06FF`, `0x0750..0x077F`) while replacing unsupported Latin diacritics with `?`, and `previewLines` decodes line buffers as UTF-8 so Arabic and bilingual (`en / ar`) receipts round-trip cleanly.
- D-178 One open shift per staff member is enforced at the database level by a partial unique index on `{ openedBy: 1 }` where `{ status: 'open' }`. Cashiers without `shift.view` can only view, move cash in, or close their own shift (`SHIFT_CLOSE_FORBIDDEN`), and if `pos.shiftMaxDiscrepancy > 0`, a cashier without `shift.view` cannot close a shift whose `|closingCash - expectedCash|` exceeds that limit (`SHIFT_DISCREPANCY_TOO_LARGE` — a manager with `shift.view` must close it).
- D-179 Cash sales in `summarizeShift` are computed net of `changeGiven` (`sum(cash tender) - changeGiven`, floored at 0 per order) so overpaid cash tenders reconcile with the actual physical cash retained in the drawer.
- D-180 Closing a shift writes an immutable `ZReport` document (`z_reports` collection, guarded by Mongoose pre-hooks against `updateOne`/`findOneAndUpdate`/`deleteOne`/`deleteMany`) inside the same transaction as the shift close and gapless `Z-` counter, preserving the point-in-time snapshot forever while `GET /shifts/:id/x-report` recomputes live from current shift orders.
- D-181 Returned line pricing (`priceReturnedLines`) pro-rates `lineTotal`, `net`, `vat`, and `discountTotal` from the original order's snapshotted line, and when a return exhausts the remaining returnable quantity of a variant (`priorQty + returningQty === originalQty`), it assigns the exact remaining `lineTotal / net / vat / discountTotal` so multi-step partial returns always sum to 100% of the original line with zero halala drift.
- D-182 Damaged returns (`disposition: 'damaged'`) book a `return` stock operation (`+qty`) followed immediately by an `adjust` stock operation (`-qty`, `reason: 'damaged'`) inside the same transaction so the stock ledger records both the customer return and the damaged write-off while keeping sellable on-hand stock accurate. When a customer is attached to a refunded return, `EVENTS.LOYALTY_REVERSED` is emitted with `{ returnId, returnNo, orderId, orderNo, customerId, amount }` so P7.1's loyalty ledger subscriber claws back the points earned on the returned amount.
- D-183 The loyalty ledger is append-only and strictly immutable (`loyalty_ledgers` collection, guarded against `updateOne`/`updateMany`/`findOneAndUpdate`/`deleteOne`/`deleteMany` by model pre-hooks). Point changes (`earn`, `redeem`, `reverse`, `adjust`, `expire`) are recorded with signed deltas and post-transaction balances, preventing negative customer balances at the database level (`$gte: -delta` condition on balance deductions).
- D-184 Loyalty earning (default 100 SAR spend = 1 pt, configurable via `loyalty.earnSpendRate`) is idempotent on `orderId` via ledger lookup: `ORDER_PAID` or `ORDER_COMPLETED` will award points exactly once even if re-emitted or retried.
- D-185 Loyalty reversals on refunded returns claw back points via `EVENTS.LOYALTY_REVERSED` up to the customer's current points balance without forcing balances negative.
- D-186 Point expiry is configurable via `loyalty.expiryDays` (default 365 days; 0 = never expire). Earn transactions record `expiresAt`, and the expiry sweep writes an `expire` record to the ledger for past-due batches idempotently.
- D-187 Customer segments (P7.2) are derived dynamically via shared pure function `deriveCustomerSegment()` and database aggregation: VIP (lifetime spend >= 2,000 SAR or gold/platinum loyalty tier), Loyal (>= 3 orders), New (registered <= 30 days ago and <= 1 order), Active (purchased <= 60 days ago), Slipping (purchased between 60 and 120 days ago), Churn risk (purchased > 120 days ago), and Idle (0 orders and registered > 30 days ago). This shared rule powers customer admin filtering and marketing campaign targeting (P7.3).
- D-188 Campaigns (P7.3) support both email and SMS channels with audience targeting based on customer segments (all, vip, loyal, active, new, slipping, churn_risk, idle). Marketing opt-outs are tracked per channel (`marketingOptOut.email`, `marketingOptOut.sms`) on the customer record, and unsubscribe links use signed HMAC-SHA256 tokens (`/api/v1/campaigns/unsubscribe?token=...`) allowing safe, one-click opt-out without authentication. Campaign templates use `LocalizedString` with automatic translation, dispatching messages in each customer's preferred language. Immediate or scheduled BullMQ dispatch logs individual delivery statuses in `campaign_deliveries` with retries and rate limiting.
